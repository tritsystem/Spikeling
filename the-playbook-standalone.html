Syntax glossary

Every repo chapter below has a real, unedited excerpt from that repo's actual source, typed in line by line. Rather than re-explain what a function is fourteen separate times in fourteen languages, here's every generic building block, once, in plain terms. Each per-line explanation later just points back here for the generic part and spends its words on what's actually specific to that line.

variable / assignment
A named box that holds a value. x = 5 means "put 5 in the box named x." x -= 1 means "take whatever's in x, subtract 1, put the result back in x."
function / def / fn / func
A named, reusable block of steps. You "call" it by name with some inputs (parameters) and it can hand back a result (return). Every language here spells the keyword differently — def (Python), fn (Rust), func (GDScript) — same idea.
parameters / arguments
The named inputs a function expects, listed in its parentheses. def f(x, y) — when you call f(3, 4), x becomes 3 and y becomes 4 for that one run.
return
Hands a value back to whoever called this function, and stops running the rest of the function immediately.
type annotation
: float, -> bool, : int — a label saying what kind of value is expected. It's documentation the language itself can check; it doesn't change what the code does.
if / else / elif
A fork: run this block if a condition is true, otherwise run that one. elif (Python) / else if just chains another condition onto the same fork.
for loop
Repeats a block once per item in a list, or once per number in a range. for i in range(5) runs the block with i = 0, 1, 2, 3, 4.
indentation defines blocks
In Python and GDScript, how far a line is indented (not braces) says which if/for/function it belongs to. Two lines indented the same amount under an if both run when that condition is true.
{ } braces define blocks
Rust and SystemVerilog use curly braces instead of indentation to mark where a block starts and ends — indentation there is just for human readability, the braces are what the language actually reads.
class / struct
A blueprint bundling related data together (and sometimes the functions that act on it). One "instance" of a class/struct is one real object built from that blueprint — e.g. one specific neuron with its own potential and threshold.
self / &mut self
self means "the specific instance this function was called on." Rust's &mut self additionally says "and this function is allowed to change that instance's own data," not just read it.
list / array / Vec
An ordered sequence of values you can loop over, index into (list[0] is the first item), or append to.
dict / Dictionary / HashMap
A lookup table: stores values under named keys instead of numbered positions. d["foo"] fetches whatever was stored under the key "foo".
comment
Text the language ignores entirely — # in Python/GDScript, // in Rust/SystemVerilog. Purely for the human reader.
docstring / doc comment
A comment placed right after a function's signature (often in triple quotes """like this""" in Python, or /// in Rust) documenting what that function does. Still just a comment — ignored when the code runs.
f-string / string formatting
A string with {variable} slots that get replaced with real values when it runs. Python: f"V={v}". Rust's format!(...) does the same thing.
boolean
A value that's only ever true/True or false/False — the result of any yes/no question the code asks, like v >= threshold.
Foundation 01

The LIF spiking neuron

Every Spikeling-based system in this portfolio — tribe, sensor-duo, pond-health, server-guard, spikeling-os, llama-demo — is built on one small mechanism. Get this exactly right and a dozen repos get easier, not harder.

Understand

What is a neuron actually doing, mechanically, on every single tick?
Its membrane potential accumulates weighted input from every synapse and external stimulus that tick. Then it leaks toward zero by a fixed amount (leak). If the resulting potential is at or above threshold and it isn't currently refractory, it fires: emits a spike, resets its potential, and enters a refractory window during which it cannot fire again no matter how much input arrives.
Why "leaky" specifically — what breaks without the leak term?
Without leak, a plain accumulator, any tiny sustained noisy input eventually crosses threshold no matter how weak, because nothing ever comes back down. Leak is what makes the neuron a coincidence / recency detector instead of a lifetime counter — it can tell "strong signal happening right now" apart from "weak signal that's been dribbling in forever," which a plain sum cannot.
In this repo's own zombie.gd, one refractory period replaced two separate hand-rolled mechanisms. Which two, and why did one neuron's own physics cover both jobs?
It replaced a retarget-cooldown timer and a separate hysteresis gate class. A neuron in refractory literally cannot re-fire — that alone throttles how often a new target commitment can happen (the timer's job) and prevents flip-flopping between two near-equal targets, because the currently-committed target persists through the whole refractory window instead of being re-evaluated every tick (the hysteresis gate's job). One real mechanism, two jobs, because both jobs were really the same constraint wearing different names.
Why does bounded, relaxing Hebbian learning matter for keeping two agents' "personalities" distinct over a long session (tribe's Wary vs. Trusting NPCs)?
Synapses strengthen when source and target both fire (Hebbian), but the strengthening is bounded and relaxes back toward an innate value over time. Without that relaxation, weights would saturate in one direction permanently — a long enough session would wash every NPC's behavior into the same saturated extreme, erasing the distinction between a Wary and a Trusting brain that the innate starting weights were built to express.

Build it from scratch

  1. State: one float, potential = 0, plus a refractory_remaining counter.
  2. Each tick: potential += sum(weighted synaptic input this tick), then potential = max(0, potential - leak).
  3. Fire check: if potential >= threshold and refractory_remaining <= 0: emit a spike, set potential = 0, set refractory_remaining = refractory.
  4. Otherwise: refractory_remaining = max(0, refractory_remaining - 1).
  5. Optional Hebbian/STDP: on fire, strengthen synapses whose source fired shortly before this neuron fired; clamp the weight and let it relax back toward its innate strength each tick it isn't reinforced.
  6. Compile once, run everywhere: Spikeling's actual trick is describing this in one small text grammar (neuron / connect / action / refractory / learn) and generating four different runtimes off the same description — Python for iteration, C for embedded, Verilog for FPGA, GDScript for a game.

Foundation 02

Ternary computing

{−1, 0, +1} instead of {0, 1}. The whole "trit" line — 012-trit-search, observe-api, methodlm's second witness — runs through this idea, and its own README is unusually blunt about where it costs more than it's worth.

Understand

What's the real value proposition of a third state — not "more range," what does it actually buy that binary structurally can't?
Two concrete things. First, balanced ternary is natively signed — a digit string's value can be negative just by leading with a −1, with no separate sign bit or two's-complement trick required. Second, the third state gives you a genuine "unknown / no-consensus" value as a first-class citizen, not an encoding hack bolted onto a 2-state system — which is exactly what a CONSENSUS gate needs: output +1 if every input agrees +1, −1 if every input agrees −1, and 0 otherwise. Binary AND/OR can't express "everyone agrees" vs. "nobody agrees" vs. "mixed" as three distinct outputs without extra machinery.
Ternary weight compression measured 20× smaller at a 7.35pp accuracy cost. INT8 measured 4× smaller at 0.19pp. What does that comparison actually tell you, beyond "ternary compresses more"?
Compression ratio and accuracy loss are not proportional — 5× more compression bought roughly 38× more accuracy damage. That's the real, disclosed reason observe-api ships float32 embeddings in production, not ternary, even though it's built directly on the ternary-search codebase: the research thesis and the shipping engineering decision honestly diverge, because the measured numbers said so.
The RTL consensus gate measured 1.4× fewer instructions than a software fallback. An earlier informal claim said "10×." Why keep the boring number in the README?
Because the 1.4× is what was actually measured, and the 10× was never verified — it was the kind of round, appealing number that spreads informally. Publishing the real 1.4× instead of the nicer- sounding 10× is the portfolio's whole research discipline, condensed into one number.

Build it from scratch

  1. Define a trit type over {−1, 0, +1} and pick a storage encoding (2 bits per trit is simplest; packed base-3 is denser).
  2. Implement NOT (negate) and ADD with carry, in base 3.
  3. Implement the CONSENSUS gate: N trits in, +1 only if all are +1, −1 only if all are −1, 0 otherwise — this is the operation where the third state actually earns its keep over binary logic.
  4. Write it once in a hardware description language (SystemVerilog: trit_pkg, trit_register, trit_add, consensus_gate) and simulate against a real testbench — the actual repo runs 36/36 real cases clean.
  5. Be explicit about the honest boundary: simulated-in-iverilog is not the same claim as synthesized-on-real-silicon. Say which one you've actually done.

Foundation 03

Physical / analog reservoir computing

Underlies the whole physics research cluster: quasicrystal-mems-reservoir, symmetry-selection-rule, topological-phononics.

Understand

What is a "reservoir," mechanically, in one sentence — not the brain metaphor?
A fixed, untrained, sufficiently nonlinear dynamical system that you drive with an input signal and read out linearly. You never train the reservoir itself — only a cheap linear readout on top of it. Its whole job is to nonlinearly mix and remember recent input history richly enough that a linear readout can extract something useful from that mixture.
Why does breaking D4 symmetry on a MEMS plate revive computation, mechanically — what does the ∫φ³ mode overlap have to do with anything?
∫φ³ (the cubic mode overlap) is the strength of the nonlinear term that lets an oscillator actually mix input information instead of just linearly filtering it — a purely linear reservoir can't compute anything a linear filter couldn't. Under exact D4 symmetry that overlap vanishes for 7 of 8 modes (proved by group theory, confirmed against real finite-element mode shapes to 1 part in 10⁹), silencing most of the reservoir's computational capacity. Aperiodic perforation breaks the symmetry and revives those modes.
State topological-phononics' real result precisely — not the sound-bite version.
Topological structure protects a reservoir against a dead element exactly when, and only when, chiral symmetry holds. The advantage is several-fold in the idealized model, measurably weaker under real nonlinearity, weaker again under noise, beaten outright by plain redundancy as an alternative strategy, and only marginal / statistically inconclusive in a realistic damped device model. The idealized magnitude does not transfer to hardware — the chiral boundary condition is the part that does.

Build it from scratch

  1. Build or simulate a fixed nonlinear dynamical system: coupled oscillators, an SSH chain, or a real finite-element plate model.
  2. Drive it with an input stream and record its internal state trajectory over time.
  3. Train only a linear readout (ridge regression) mapping recorded states to a target task (linear memory, NARMA10).
  4. To test a defect-tolerance hypothesis: kill one element, re-measure task performance, compare two coupling regimes (e.g. topological vs. trivial dimerization).
  5. Pre-register the hypothesis and the exact test before running it — this is not optional housekeeping, it's the actual method this whole cluster of repos was built under.

Foundation 04

Causal reasoning: adjustment & robustness value

The engine under methodlm and llama-demo's Root Cause Copilot.

Understand

Use the real measured sex/diabetes example: why is raw correlation actively dangerous, not just imprecise?
sex ranked dead last by both raw correlation (+0.043) and Random Forest importance (0.012) — both standard tools said "irrelevant, ignore it." Backdoor adjustment showed it actually survives with RV = 0.17, and its adjusted effect is sign-flipped and an order of magnitude larger (−0.19). Its real negative effect was being cancelled in the raw number by its positive correlation with three other genuine drivers (bmi, bp, ltg). Trusting the naive ranking would mean discarding a real driver entirely.
What does a robustness value of 0.31 actually tell you that a p-value can't?
RV measures how strong an unmeasured, hidden confounder would need to be to fully explain away the observed effect. RV < 0.10 means the finding is fragile — a weak hidden confounder could kill it. A p-value is a statement about the data you collected; RV is a statement about robustness to the data you didn't collect.
Why does "just adjust for everything you've got" fail as a strategy?
Conditioning on a collider — a variable caused by both the treatment and the outcome — introduces bias rather than removing it (the "Table 2 fallacy"). This is why the harness runs a collider/mediator audit before adjustment instead of blindly controlling for every available column.

Build it from scratch

  1. Implement raw correlation as the visible baseline — keep it, don't hide it, so any improvement over it is honestly checkable.
  2. Implement backdoor adjustment: regress the target on treatment + named confounders, read off the treatment's coefficient.
  3. Implement a Cinelli–Hazlett robustness value on top of that adjustment.
  4. Implement a collider check: is this control variable downstream of both treatment and outcome? If so, flag it — don't adjust for it blindly.
  5. Enforce pre-registration in code: no FINAL verdict accepted until at least one real test (ADJUST / STRAT / RUN) has actually executed. Make the discipline a hard gate, not a suggestion.

Foundation 05

Trend vs. spiking: the dual-detector pattern

Born in pond-health, extracted as sensor-duo, reused in server-guard.

Understand

What's the precise tradeoff between the two detectors — not "one's better," the real mechanism?
The trend detector fits a line through recent readings and projects it forward — real early warning, at the cost of sometimes alerting on a trend that reverses before it actually crosses the danger line. The spiking detector (an LIF neuron, Foundation 01) never does that: a single noisy reading can't cross threshold on its own — it only fires once several consecutive stressed readings genuinely integrate past threshold, or instantly on a truly critical one. But it has no forecasting ability; it only confirms a problem that's already real and sustained.
Neither one is "strictly better." What's the actual design implication for how you use both together?
Run both, and treat disagreement between them as the interesting signal — that's the explicit stated design intent, not an afterthought bolted on because two detectors seemed fancier than one.

Build it from scratch

  1. TrendDetector: rolling window per channel, linear fit, project forward, estimate threshold-crossing time.
  2. SpikingDetector: map each channel's stress level to a stimulus current into a dedicated LIF neuron; let leak/refractory naturally reject single-sample noise.
  3. Log both to SQLite; generate a Grafana dashboard reading straight from it.
  4. Generalize: parametrize over an arbitrary set of named channels with a per-channel Range(stress_low, stress_high, critical_high) instead of hardcoding five pond-specific parameters — this exact step is the real sensor-duo extraction from pond-health.

Foundation 06

The research discipline itself

This is the connective tissue under every chapter that follows — more important than any single repo.

Understand

Pick spikeling-os's Milestone 4 negative result. Why does reporting it honestly make the rest of the portfolio more credible, not less?
Trivial coupling beat topological coupling on scheduling fairness (0.860 vs. 0.790) — the opposite of the hypothesis. It was reported exactly as measured, with an honest root-cause guess (the coupling term was deliberately kept weak to avoid instability, and there's a real open question whether a discrete winner-take-all accumulator is even the right dynamical regime for topological protection at all). A portfolio that only ever reports confirmations can't be trusted when it does report a win — the negative results are precisely what makes the positive ones worth believing.
What specific, repeatable process produces this kind of honesty — not the personality trait, the mechanism?
Pre-registration. The hypothesis and the exact test are written down before the experiment runs, which removes the room to quietly redefine "success" after seeing an inconvenient result. The same discipline is enforced in software by methodlm's FINAL-verdict gate — it's not just a research habit, it's a thing you can point to in actual code.

Spikeling

github.com/tritsystem/Spikeling

The neuromorphic DSL + runtime. Write one .spk file, run it on four backends. The substrate under most of the rest of this playbook.

Understand

Why compile one description to four backends instead of writing four separate implementations?
The .spk file is the single source of truth for topology and parameters. Each backend only needs a codegen/interpreter for the same small grammar, instead of four hand-written implementations of neuron/synapse semantics silently drifting apart from each other over time.
Four neuron types exist — LIF, Izhikevich, AdEx, Resonator. When do you reach for Resonator over plain LIF?
Resonator is a damped oscillator that responds only to input near its own frequency — a frequency-domain primitive, not a threshold-crossing one. Reach for it when you want frequency-selective response (this is what the acoustic noise-cancellation work in this portfolio actually uses).

Build it from scratch

  1. Design the .spk grammar: neuron / connect / action / refractory / learn.
  2. Write a parser/compiler for it.
  3. Implement the Python interactive runtime as the reference implementation (Foundation 01's LIF step).
  4. Add STDP learning on top.
  5. Add a C codegen backend for embedded targets.
  6. Add a Verilog codegen backend for FPGA.
  7. Add a GDScript backend (a compact synapse SRC -> DST weight=N variant) for Godot game AI.

quasicrystal-mems-reservoir

github.com/tritsystem/quasicrystal-mems-reservoir

Same day as Spikeling. The FEM study behind Foundation 03's D4 selection rule, replicated on three separate substrate classes.

Understand

"Confirmed to 1 part in 10⁹" — confirmed against what, exactly?
The group-theory proof that ∫φ³ vanishes for non-totally-symmetric D4 modes was checked numerically against real finite-element-computed mode shapes. It's an independent numerical confirmation of an analytic prediction, not just the analytic derivation standing alone.
The rule only replicated on other substrates once a "capability gate" was satisfied first. What does that precondition tell you about how strong the underlying claim really is?
The selection rule isn't an unconditional law — it's conditional on the substrate already being capable enough to show any nonlinear computation at all. State the boundary honestly: "the rule holds given a capability floor," not "the rule always holds."

Build it from scratch

  1. Homogenized finite-element plate-bending solver: mesh, boundary conditions, modal analysis.
  2. Compute mode shapes/frequencies for a perforated (quasicrystal-pattern) plate.
  3. Derive, then numerically verify, the D4 point-group selection rule on ∫φ³ mode overlaps.
  4. Wire the mode data into a reservoir readout — train only a linear readout on the modal response to an input signal.
  5. Test generality by replicating on further substrate classes (a coupled resonator bank, a discrete lattice ring) — pre-register a capability-gate check before each replication attempt.

tribe

github.com/tritsystem/tribe

Every NPC — tribe members, animals, rival tribes — runs a small Spikeling LIF brain instead of a behavior tree. Trust ranks gate risky orders; inter-tribe war converges with no forced winner.

One brain per AI tribe, not per individual member. Why that granularity, specifically?
Cost. Per-member brains at "Epic" scale would hit the same O(n) blowup class as horde-defense-beta's turret target-scan bug. One brain per tribe is cheap enough to run many tribes simultaneously.
What actually keeps the tribe DSL cheap at scale with many tribe instances sharing archetypes?
Parsed .tribe results are cached per archetype name — many tribe instances share one parse instead of every instance re-parsing the same text file.

Build it from scratch

  4. Procedural "aliveness" animation layer driven by the brain's own tension/mood output channels.
  5. Inter-tribe war: physical marching war parties, siege logic, no-forced-winner convergence.
  6. Scale presets (Skirmish / Standard / Epic) — profile physics-frame ms first before guessing at fixes; the real bottlenecks (LOD, hive-brain granularity, MultiMesh rendering) only show up at Epic.

methodlm

github.com/tritsystem/methodlm · sibling to OBSERVE

A verifiable causal-reasoning harness (Foundation 04). On a confounded-scenario benchmark, its backdoor-adjustment test cuts false causal claims from 100% to ~1% while keeping 100% detection of the true cause.

Understand

"The discipline, not the model, is the product." What enforces that, in actual code?
The same pre-registration gate — no FINAL without a real ADJUST/STRAT/RUN test — applies whether the backend is a small local model or a frontier Claude model. The gate, not the model's own judgment, is what produces trustworthy output.
What's the demonstrated failure mode of "the same model, minus the method" in the head-to-head race mode?

CollectorRegistry runs every collector each tick through one uniform collect() -> {name: value} interface, and isolates failures per-collector so a flaky collector can't kill the tick. A new collector is a new file implementing that one method — nothing else in the codebase changes.

Because nothing was actually broken in the failure-mode sense — the collector ran exactly as designed, on schedule, successfully, every single time.
